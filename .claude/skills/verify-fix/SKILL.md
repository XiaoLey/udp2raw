# verify-fix:改动验收方法论

验收要回答两个问题,缺一不可:

1. **改动确实解决了问题**——不是"看起来不崩了",而是有「改前能复现、改后消失」的对照证据
2. **正常功能没被改坏**——改前能跑通的,改后必须同样跑通

## 第零铁律:不得波及生产环境

本机同时运行着投入生产的 udp2raw(配合 WireGuard),测试一旦碰它后果严重(详见项目 AGENTS.md「测试与环境安全」):

- **清理只杀自己起的进程**:按记录的 PID / 进程组精确杀;sudo 起的进程用 `setsid` 启动、`kill -9 -- -PID` 杀整组(kill sudo 的 PID 只会让子进程变孤儿继续跑)。**永远禁止** `pkill -f <程序名>` 之类按名字模式的全量清理
- **iptables 只删自己建的**:阶段开始前 `iptables-save` 快照,结束时按快照差异删除新增的规则和链,绝不按链名模式批量 flush/删
- **用不常见的测试端口**(如 31xxx 段),避开生产配置
- **动过 iptables 后**习惯性 `sudo wg show | grep -A2 transfer` 瞄一眼握手时间,确认生产隧道没被波及
- 清理命令的 pkill 模式别出现在执行该命令的 shell 命令行里,否则 pkill 会杀掉自己所在的 shell(可用 `pas[s]` 这类字符类写法绕开自匹配)

## 阶段一:对照复现(证明"改前坏、改后好")

先构建基线:把改动前的提交用 `git worktree add` 检出到 /tmp,用**同一 makefile** 编译(常规版 + `make debug2` 的 ASan 版)。按 bug 类型选观测手段:

| bug 类型 | 手段 |
|---|---|
| 缓冲区越界 / 溢出 | ASan(`make debug2`)同输入新旧对照;旧版报告的栈帧应精确落在修掉的那几行 |
| 空指针 / 崩溃 | CLI 输入直接复现;旧版 SEGV vs 新版干净报错退出 |
| 未初始化内存读取 | valgrind memcheck;对照两版的报告**位置集合**(`at` 行),别比总数——glibc/AES 有固定背景噪音 |
| 竞态 | 先分析结构性触发条件(如 epoll level-triggered 下常驻可读 fd 永远排在就绪队列前部,单事件批次是常态 → 自然复现可能结构上不可行);再**故障注入**:给新旧两份 scratch 构建注入同一段代码,只构造竞态前提(如"处理事件前关掉它对应的 fd"),被测分支保持原样,对照行为 |
| 错误路径(资源耗尽等) | sysctl / ulimit 把上限收紧到让错误分支**自然**触发;注意先测量既有基线(如 root 已持有的 epoll watch 数、其他进程的占用),上限值要动态算 |
| 超时 / 心跳状态机 | iptables 单向 DROP 模拟非对称链路;用 `--log-level 5` 让 debug 级日志可见,做日志断言 |

断言要落在可观测差异上:进程存活、ASan/valgrind 报告、特定日志行及其相邻关系、退出方式(assert 崩溃 vs 受控退出,后者还影响清理是否执行)。

## 阶段二:正常回归(证明"原来能跑的还能跑")

- **E2E 数据流**:旧+旧(基线自身可用是测试有效的前提)、新+新,双向 UDP echo,多种包长(小包 / 1000 / 接近 MTU)
- **跨版本互通**:旧 client + 新 server、新 client + 旧 server——这是"协议、密钥派生、解析语义未被改变"的最强证据,混跑握手和数据流都正常才算过
- **CLI 等价**:受影响选项的正常用法(含配置文件加载)新旧行为一致

## 阶段三:报告

- 证据表:测试项 | 旧版结果 | 新版结果
- 明确区分「有新旧对照实证」与「仅代码级推理」——确实触发不了的(如天文级概率的未初始化窗口),说明为什么测不到,别冒充测过

## 常见坑(都踩过)

- `grep -m1` 抓标记行会抓到先出现的无关行(如 ASan 报告排在 WARN 之后)——存疑就看原始输出
- 传环境变量进 sudo 进程用 `sudo env VAR=1 cmd`
- 断言依赖的日志行可能在 log_trace/log_debug 级,默认不显示——先确认级别
- 别用 `2>/dev/null` 吞 stderr,失败时那是唯一线索
- epoll 批次几乎总是单事件:靠"同批次残留"的竞态自然复现极难,优先故障注入
- sysctl/ulimit 类测试:上限值要减去系统既有占用动态计算,且必须保存原值、结束必恢复

## 本仓库现成套件

`tests/` 是本方法论的可运行实现,改完东西可以直接跑:

```bash
tests/run_all.sh <改动前的提交>    # 全量对照验收
tests/run_all.sh                  # 只测当前版本自身功能
```

各脚本对应的手段见 `tests/README.md`。新增测试时复用 `tests/harness.sh` 的 `begin_phase`/`end_phase`(安全清理)、`start_server`/`start_client`/`echo_check` 等辅助函数,别另起清理逻辑。
